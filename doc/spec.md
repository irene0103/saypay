## 1. 專案概述

### 1.1 一句話定位

一筆輸入，同時完成 **記帳 + 分帳 + 統計 + 欠款更新**。

### 1.2 解決的問題

| 痛點 | SayPay 的解法 |
| --- | --- |
| 記帳與分帳需重複輸入 | 單一交易同時承載兩者（見 §1.4） |
| 個人「實際花費」不準 | 以 `shareAmount` 而非 `amount` 計算實際支出 |
| 無法統整欠款 | 自動化 pairwise 淨額結算 |
| 聚餐 / 旅遊 / 情侶分帳麻煩 | 群組收納 + 一鍵結清 + 分享連結 |
| 缺少快速輸入 | 語音 + 自然語言解析 |

### 1.3 產品形態

| 對象 | 需求 | 實作 |
| --- | --- | --- |
| **我（帳本擁有者）** | 記帳、分帳、統計、跨裝置 | 登入帳號，資料存雲端 |
| **分帳對象（A、B、Amy…）** | 只需看到「我欠多少」 | **不需帳號**，開分享連結即可（§3.11） |

**MVP 做：** PWA、Auth（僅擁有者）、IndexedDB 本地優先 + Supabase 同步、公開唯讀分享連結。
**MVP 不做：** 對方登入、即時協作、對方寫入、多幣別、債務簡化（§5.5）、催收、群組預算。

### 1.4 核心模型：一筆交易，兩種讀法

> **範例：我、A、B 吃火鍋 $600，我墊全額，三人平分。**

這是**一筆** Transaction，不是兩筆。

```ts
{
  title: "火鍋",
  amount: 60000,           // $600（以「分」為單位）
  paidBy: "me",
  members: ["me", "A", "B"],
  splitType: "equal",
  splits: [
    { member: "me", shareAmount: 20000 },  // ← 這就是「記帳：火鍋 200」
    { member: "A",  shareAmount: 20000 },
    { member: "B",  shareAmount: 20000 },
  ]
}
```

| 讀法 | 值 | 用在哪 |
| --- | --- | --- |
| 現金流出 | `$600` | 帳本列表主金額、墊付款統計 |
| **我的實際花費** | `$200` | Hero 卡、預算、分類占比、月趨勢 |
| 產生的債務 | A 欠我 $200、B 欠我 $200 | 分帳頁、欠款雙卡 |

**帳本列表顯示規則：** 主金額顯示 `$600`，右下角小字 `分帳 · 我的 $200`。

理由：列表是「發生了什麼」的事實記錄，$600 才是這頓飯的真相；$200 是衍生值。若列表直接顯示 $200，使用者對信用卡帳單時會找不到那筆 $600。

## 1.5 競品對照與定位

參考台灣主流記帳 App：**天天記帳**（完整型）與**簡單記帳 SMoney**（輕量型）。

### 1.5.1 兩者的定位光譜

| | 天天記帳 | 簡單記帳 | **SayPay** |
| --- | --- | --- | --- |
| 定位 | 完整財務管理 | 三秒記帳、養成習慣 | **記帳 + 分帳合一** |
| 記帳 | 深（多帳本、子分類、固定收支） | 淺而快 | 中（刻意只留金額 / 類別 / 日期 / 備註） |
| 資產負債 | ✅ 銀行 / 信用卡 / 股票 / 外幣 | ❌ | ❌ **不做** |
| 分帳 | ❌（僅「花在誰身上」標籤） | ❌ | ✅ **核心** |
| 發票載具 | ✅ | ✅ 自動記帳 | 🔮 長期目標 |
| 共享 | iCloud 共同帳本 | 共享帳本 | 唯讀分享連結 |

### 1.5.2 值得借鑑的（已納入本規格）

| 功能 | 來源 | 納入處 |
| --- | --- | --- |
| 「再記一筆」保留上一筆的類別／成員 | 天天記帳 | §3.2.1 |
| 金額鍵盤內建計算機 | 天天記帳 | §3.2.1 |
| 日曆檢視（每日收支一目了然） | 兩者皆有 | §3.1.1（`1b` 提前） |
| 記帳提醒（自訂時間） | 簡單記帳 | §3.9 |
| 連續記帳天數 streak | 簡單記帳「連勝日曆」 | §3.1.1 |
| 子分類（餐飲 → 外食 / 食材 / 零食） | 天天記帳 | §4.6 `Category.parentId` |
| CSV 匯出 | 兩者皆有 | §3.12 |
| 密碼鎖 / 首頁隱藏金額 | 兩者皆有 | §3.6 |
| 雲端同步免資料遺失 | 兩者皆有 | §3.12、§6.1 |

### 1.5.3 明確不做的（Non-goals）

> 這份清單比「要做什麼」更重要。

| 不做 | 理由 |
| --- | --- |
| 多帳本 | 分帳已提供「群組」維度收納旅遊 / 專案，語意重疊 |
| 資產負債管理（銀行 / 現金餘額 / 淨資產） | 需要「初始餘額」「對帳」概念，複雜度倍增 |
| 帳戶間轉帳（ATM 領錢、儲值） | 附屬於資產管理，同上 |
| 股票 / 投資損益 | 完全不同的產品 |
| 信用卡帳單、分期、自動繳款 | 同上 |
| 多幣別 / 匯率 | 旅遊分帳會想要，但先確保核心正確 |
| 固定收支自動生成 | Phase 11 再評估 |
| **帳戶 / 付款方式**（現金、LINE Pay、信用卡） | 無任何功能依賴它——不影響預算、分帳、債務矩陣。留著只是多一個輸入步驟，拖慢「三秒記帳」。Wireframe `1d` 的該欄位移除 |
| **標籤（tag）** | 與「群組」職能重疊。分類是互斥維度、群組是可疊加維度，已足夠。再加第三個維度只會讓使用者困惑「這筆該放群組還是貼標籤」 |
| **同裝置多使用者切換** | 匿名帳號的固有限制，見 §3.12 L0 |

**理由：** 天天記帳是做了十年的成熟產品，功能廣度不可能追上，也不需要追。SayPay 的差異化在於**市面上的記帳 App 分帳都很弱，而 Splitwise 不能記帳**。核心價值是 §1.4 的那筆火鍋——一筆輸入同時滿足兩邊。追求功能廣度只會做出一個更差的天天記帳，而分帳依然沒做好。

### 3.2 新增記帳 ＋ 分帳輸入

| 代號 | 流程 | MVP 決策 |
| --- | --- | --- |
| **1d** | 單頁表單 + 分帳開關 | ✅ 表單基底、編輯態、離線降級終點 |
| **1e** | 自然語言優先 → 解析確認卡 | ✅ 預設入口 |
| 1f | 兩步驟精靈 | 延後 |

> **架構要求：** `1e 解析確認卡` 與 `1d 表單` 共用同一份 `TransactionDraft` state model。兩者是同一份資料的兩種呈現，可隨時互切而不遺失內容。這是離線降級與後續換 LLM 解析的前提。

#### 3.2.1 單頁表單（1d）

| 區塊 | 欄位 | 備註 |
| --- | --- | --- |
| 類型切換 | `支出` / `收入` | **收入不可分帳**（§5.6） |
| 金額 | 大數字輸入 | |
| 類別 | 餐飲 / 交通 / 娛樂 / …（支援子分類） | |
| 日期 | 預設今日（本地時區） | |
| 備註 | 選填 | |
| **是否分帳** | Toggle | ON 時展開以下 |
| ─ 付款人 | 預設「我」 | 單一付款人（§5.6） |
| ─ 參與者 | 頭像多選 + `+` | **上限 20 人**；付款人不一定在內（純代墊） |
| ─ 分帳方式 | `平均` / `指定金額` / `百分比` | |
| 底部 | 即時分帳結果預覽 | `我 $200 · A $200 · B $200` |

**多人（>6）UI 規則**

| 情境 | 處理 |
| --- | --- |
| 參與者頭像列溢位 | 顯示前 5 個 + `+15`，點擊展開全選面板 |
| 快速帶入 | 提供「從群組帶入」按鈕，一次加入整組成員 |
| `指定金額` 20 列輸入 | 提供 **「剩餘自動分攤」**：輸入前幾人金額後，勾選的其餘人平分剩餘額 |
| 上限 | 20 人。達上限時 `+` 按鈕 disabled，提示 `單筆最多 20 人` |

**即時校驗（阻擋儲存）**

- `custom`：`Σ shareAmount ≠ amount` → `還差 $120` / `超出 $50`
- `percentage`：`Σ % ≠ 100` → `目前 90%`
- 分帳 ON 但參與者為空 → 提示補上

**快速記帳體驗（借鑑天天記帳 / 簡單記帳）**

> 目標：**單筆一般記帳 3 秒內完成。** 記帳 App 的最大死因是「麻煩」。

| 功能 | 規範 |
| --- | --- |
| **金額鍵盤內建計算機** | 支援 `+ − × ÷`。`180+50` 直接算出 230。分帳與代墊情境高頻使用 |
| **「儲存並再記一筆」** | 儲存後表單不關閉，**保留上一筆的 `category` / `members` / `paidBy`**，僅清空金額與備註 |
| **智慧預設** | 類別預設帶入「最近最常用」；日期預設今日 |
| **常用組合** | 記錄前 5 組 `(類別, 金額, 備註)` 組合，於輸入頁頂部以 chip 呈現，一點即填 |
| 分帳 Toggle 記憶 | 預設 OFF。**不記憶上一筆的 Toggle 狀態**（避免誤把個人消費記成分帳） |

#### 3.2.2 自然語言輸入（1e）

**輸入：** `跟 A、B 吃火鍋 600 我先付 平分`

**流程：** 單行輸入框 → 智慧建議 chips → 解析中 → **解析確認卡**（逐項可改）→ `改用表單` / `確認儲存`

```txt
金額      $600
類別      餐飲
付款人    我
參與者    我 · A · B
分帳      平均｜每人 $200
          → 我 收回 $400 · A 欠 $200 · B 欠 $200
```

**解析規則與例外**

| 情境 | 行為 |
| --- | --- |
| 未提及付款人 | 預設「我」，確認卡以虛線底標示為推測值 |
| 未提及分帳方式但有多人 | 預設 `equal` |
| 提到不存在的成員名 | 顯示 `Amy（新成員）`，儲存時一併建立 |
| 相對日期（昨天／上週五） | Day.js 解析為本地日期 |
| 無法解析出金額 | **不進確認卡**，落到 1d 表單並帶入原句到備註 |
| 解析信心度低 | 仍進確認卡，可疑欄位虛線標示 |
| 解析出 >20 位參與者 | 拒絕解析，導向 1d 表單 |

> **鐵則：解析結果永不自動儲存**，一律經使用者確認。

Step 1 記帳 → Step 2 分帳。Header 顯示 `分帳 (2/2)` 與 `完成`。

### 3.3 分帳總覽 / 欠款統整

**MVP 採合併版：人員淨額（1g）為主視圖，群組（1h）為次分頁。**

> **單一真實來源：債務掛在「人」身上。群組僅為檢視用的篩選器（view），不是獨立帳本。**
> 依據：錢是人與人之間的債務。Splitwise 等主流工具的群組頁餘額僅為「該群組內交易的小計」，最終 Settle up 永遠是人對人。

#### 3.3.1 人員清單式（1g）

**Header 三格：** `應收 $1,200 ｜ 淨額 +$900 ｜ 應付 $300`

**篩選：** `全部` / `應收` / `應付`

**人員列：** 頭像 + 姓名 · 副標（`3 筆記錄`）· 金額（綠＝應收 / 紅＝應付）· 動作 `結清` · `分享`

> 「催收」已移除。取而代之的是「分享」——產生一個唯讀連結傳給對方（§3.11）。

**底部：** `查看結清記錄` → Settlement 歷史列表

#### 3.3.2 群組式（1h）

- Header：`分帳` + `+ 群組`
- 群組卡：`沖繩挑戰 +$2,400` · 頭像群 · `12 筆記錄`
- 底部：`+ 建立群組（旅遊 / 聚餐 / 室友…）`

**與 1g 的一致性規則**

- `Settlement` **不記 `groupId`**
- 群組卡淨額 = 該群組內所有 transaction 的 pairwise 小計，**不扣結清**
- 群組卡**不顯示「未結清 N 筆」**（語意會與 1g 衝突）
- **結清入口只存在於 1g**；群組頁點人員 → 跳轉 1g 對應列
- **群組沒有預算。** 預算僅存在於個人月預算（§3.5）

#### 3.3.3 結清規則

結清為**獨立的 ledger entry**，不修改原始交易。

| 模式 | 行為 |
| --- | --- |
| 全部結清 | 金額欄預設帶入當前 pairwise 淨額，直接確認 |
| 部分結清 | 使用者輸入任意金額（不指定筆數） |

**校驗**

- 金額必須 `> 0`
- 金額 `>` 當前淨額 → 允許，需二次確認：`Amy 只欠你 $300，確定收 $500？剩餘 $200 將計為你欠 Amy`
- 結清後淨額歸零或反向，原始交易完整保留

**不可逆性**

- Settlement 可**刪除**（撤銷誤操作），不可編輯金額
- 刪除需二次確認

**與分享連結的連動**

- 結清後該對象 pairwise 淨額歸零 → **自動撤銷**其分享連結（§3.11）
- 若因刪除 Settlement 導致淨額復原，**不自動復活舊連結**，需重新產生

### 3.4 分析頁（1i）

**時間切換：** `月` / `週` / `年`

| 區塊 | 內容 |
| --- | --- |
| 分類占比 | 環圈圖 + 前 N 類（餐飲 40% $5,016 · 交通 20% $2,508 · 娛樂 15% $1,881） |
| 月趨勢圖 | 折線圖：每日花費變化 |
| 分帳統計 | `本月墊付 $3,600` / `應收 $1,200` / `應付 $300` |

#### 指標定義（三者不同）

| 指標 | 公式 | 用途 |
| --- | --- | --- |
| **本月支出** | Σ 我付出去的 `amount`（`paidBy === me`） | 現金流出 |
| **本月實際花費** | Σ 我的 `shareAmount` | **Hero 卡、預算、分類占比、月趨勢皆用此值** |
| **本月墊付款** | Σ max(0, 我付的 `amount` − 我的 `shareAmount`) | 我替別人墊了多少 |

> **關鍵決策：分類占比與月趨勢使用「實際花費」。**
> 否則代墊一頓 $600 火鍋，「餐飲」分類會記成 600 而非 200，完全失真——這正是原始需求「個人實際花費不準」要解決的問題。
> 分析頁提供 `實際花費 / 總支出` toggle，預設「實際花費」。

**收入不納入任何支出統計與預算。**

### 3.5 預算頁（1j）

| 區塊 | 內容 |
| --- | --- |
| 總預算環 | 環形進度（`62%`）+ `本月預算 $20,000 · 已用 $12,540` |
| 分類進度條 | `餐飲 6,200 / 8,000` · `交通 2,508 / 3,000` · `娛樂 2,100 / 2,000`（超支紅色） |
| 分類層級 | **僅父分類可設預算。** 子分類支出自動彙總至父分類計算 |
| 超支提醒 | `娛樂已超支 $100 · 剩餘 $1,800（本月還有 4 天）` |

> **僅有個人月預算。群組不設預算，子分類不設預算。**
>
> 子分類預算（例如單獨限制「零食 $500」）會讓「父分類預算 vs 子分類預算總和」產生一致性問題（父 $8,000 但子加起來 $9,000 該信誰？）。收益不足以支撐這個複雜度。

#### 提醒規則（即時觸發）

Transaction 寫入 / 編輯 / 刪除後同步重算該 category 的 `spent`（以**實際花費**計）。

| 門檻 | 觸發條件 | 行為 |
| --- | --- | --- |
| **80% 預警** | 由 `<80%` 跨越到 `≥80%` | Toast：`餐飲已用 80%，剩 $1,600` |
| **100% 超支** | 由 `≤100%` 跨越到 `>100%` | Toast + Dashboard 通知徽章 |

**去重：** 僅在**狀態跨越邊界的當次**觸發。已超支狀態下再新增只更新數字。狀態存於 `budgetAlertState[month][category]`，每月重置。

> 80% 預警的理由：超支提醒發生時錢已經花掉了，預警才有行為改變的價值。門檻寫死，不開放設定。

**月份邊界：** 依 `transaction.date` 的**本地時區**年月歸屬。無預算滾存。

### 3.11 分享連結（新增 · 核心功能）

> 分帳對象**不需要帳號**。他們只會收到一個網址。

#### 分享範圍（嚴格限縮）

| 可分享對象 | 內容 |
| --- | --- |
| **單一群組** | 該群組內的交易明細 + 各成員淨額 |
| **單一人員結算單** | 我 ↔ Amy 之間所有未結清交易 + 淨額 |

#### ⚠️ 隱私鐵則

分享頁**只呈現該範圍內的資料**。以下**絕不出現**在分享頁：

- 我的其他交易、其他分類、其他成員
- 我的月預算與任何統計數字
- 任何導航入口、任何寫入操作

> 若分享頁等同「整個 App 的唯讀版」，A 會看到你昨天買了什麼、你的預算、你跟 Cindy 的欠款。這是嚴重的隱私事故，必須從路由層隔離（獨立的 `/s/:token` route，不掛載主 App 的 store）。

#### 資料模型

```ts
type ShareLink = {
  id: string
  token: string              // nanoid(16)，不可猜測（約 10^28 種組合）
  scope: 'group' | 'member'
  targetId: string           // groupId 或 memberId

  detailLevel: 'total' | 'amounts' | 'full'   // 揭露層級，見 §3.11

  createdAt: string
  expiresAt: string          // 滑動過期。每次被瀏覽時重設為 now + 30 天
  revokedAt?: string
  revokedReason?: 'manual' | 'settled' | 'group_deleted'
  viewCount: number
  lastViewedAt?: string
}
```

#### 行為

| 項目 | 規範 |
| --- | --- |
| 網址 | `https://saypay.app/s/{token}` |
| 存取 | 匿名唯讀。任何持有連結者皆可看 |
| **過期** | **30 天滑動過期**（見下） |
| 撤銷 | 設定頁「分享連結管理」列出所有連結，可單筆撤銷 |
| **自動撤銷** | 對象結清完畢 / 群組被刪除時，立即撤銷 |
| 已撤銷 / 過期 | 顯示「此連結已失效」，不洩漏任何資料 |
| 索引 | `noindex, nofollow` meta + `robots.txt` 排除 `/s/*` |
| 內容 | 唯讀。若對方要回應，提供「複製結清訊息」按鈕（純前端） |

#### 過期規則：30 天滑動視窗

> **問題：** 固定 30 天過期會讓旅遊分帳（常拖數月）中途失效；永久有效則讓被遺忘的連結永遠可存取。

**解法：每次被瀏覽時，`expiresAt` 重設為 `now + 30 天`。**

```txt
建立         → expiresAt = D+30
D+20 被瀏覽  → expiresAt = D+50
D+45 被瀏覽  → expiresAt = D+75
之後無人瀏覽 → D+75 自動失效
```

| 情境 | 結果 |
| --- | --- |
| 旅遊分帳拖三個月，對方每隔幾週點來看 | ✅ 永不失效 |
| 對方看完就忘了，一個月沒再點 | ✅ 自動失效，降低外流風險 |
| 連結外流到公開場域被持續存取 | ⚠️ 不會自動失效 → 靠管理頁的 `瀏覽次數` 異常偵測 + 手動撤銷 |

#### 自動撤銷（不需等過期）

| 觸發 | `revokedReason` | 連結後續行為 |
| --- | --- | --- |
| 該對象 pairwise 淨額歸零（結清完畢） | `settled` | → **已結清終態頁**（見下） |
| 該群組被刪除 | `group_deleted` | → `此連結已失效` |
| 使用者手動撤銷 | `manual` | → `此連結已失效` |
| 30 天滑動視窗到期 | — | → `此連結已失效` |

> **注意：** 若結清後又新增了與該對象的交易，淨額不再為零。**不自動復活舊連結**，需重新產生（舊 token 已外流，不應復用）。

#### 已結清終態頁

> 若結清後直接顯示「此連結已失效」，對方（尤其 `total` 層級只看到一個數字的人）會困惑：是被封鎖了？還是我還欠錢？

`revokedReason === 'settled'` 時，連結**不顯示失效訊息**，改為終態頁：

```txt
✅ 已結清

[群組名 / 對方名字]
結清於 2026-07-10

（無明細，無金額）
（頁尾）由 SayPay 產生 · 唯讀
```

| 規範 | 說明 |
| --- | --- |
| 揭露內容 | 僅「已結清」+ 對象名 + 結清日期。**不顯示金額、不顯示明細**（無論原本 `detailLevel` 為何） |
| 保留期 | **永久。** 終態頁不含任何金額資訊，成本僅一列 DB 記錄 |
| 其他撤銷原因 | `manual` / `group_deleted` / 過期一律顯示 `此連結已失效`，不洩漏任何資訊 |

> **為何永久保留：** 業界慣例是「收據永久有效」（Stripe / PayPal / 電商訂單頁皆然）——收據的價值就在於日後翻出來仍能證明此事發生過。終態頁本質上就是一張結清收據。
> 若 90 天後轉「已失效」，對方第一次點看到「已結清」、第二次點看到「已失效」，會二度困惑是否又欠了錢。

> 這是**刻意的資訊不對稱**：結清是雙方都樂見的終點，告知對方是善意；手動撤銷則可能是刻意隔絕，不應透露原因。

#### 其他安全機制

1. `nanoid(16)` 不可猜測（約 10²⁸ 種組合，無法暴力枚舉）
2. `noindex` + `robots.txt` 排除，避免被搜尋引擎索引
3. 分享連結管理頁顯示 `瀏覽次數` 與 `最後瀏覽時間`，異常可自行撤銷
4. 滑動過期的 `expiresAt` 更新須由後端 RPC 執行，客戶端不可寫入

#### 揭露層級（`detailLevel`）

> 明細會透露你在哪裡吃了什麼、跟誰吃。但只給總額，對方又無從核對。中間需要一檔。

建立分享連結時三選一，**預設 `full`**（多數場景是朋友，透明度有助信任）。

| 層級 | 分享頁內容 | 適用 | MVP |
| --- | --- | --- | --- |
| `full` | 每筆的 `date`（日）· `title` · `amount` · 你的份額 | 朋友、情侶、室友 | ✅ Phase 5 |
| `amounts` | 每筆的 **`YYYY-MM`（月精度）** · `amount` · 你的份額。隱藏 `title`、`note`、確切日期 | 公司聚餐、不熟的群組 | 🔶 **Backlog** |
| `total` | 僅淨額 + 交易筆數 | 只想告知欠多少 | ✅ Phase 5 |

#### 為何 `amounts` 先不出

**三段揭露在業界罕見。** Splitwise 的群組成員一律看到完整明細；Google Docs 的分享只有「檢視／編輯」。多數產品是**兩檔**——第三檔的解釋成本高於價值，使用者站在分享對話框前得先讀說明才知道 `amounts` 是什麼。

**決策：Phase 5 只出 `full` 與 `total`。`amounts` 保留於 backlog，觸發條件是使用者實際反映「不想讓同事看到我們吃了什麼」。**

`detailLevel` 欄位一開始就設計成三值列舉，日後加 `amounts` 不需 migration。

#### `amounts` 的設計（實作時直接採用）

若日後啟用，**日期必須降為 `YYYY-MM` 月精度**：

- 確切日期能推測出「7/10 晚上你們在一起」，對不熟的群組仍嫌多
- 但完全拿掉日期，核對能力歸零——對方看到三筆 $600，無法判斷是三次不同聚餐還是重複計算，`amounts` 便退化成 `total`
- **月精度是唯一的平衡點：** 「7 月有兩筆」可核對，「7/10 晚上」推測不出來

> 若最終判斷連月份都不可揭露，應**直接移除 `amounts`**，而非留一個無法核對的空殼——它會給使用者「已做隱私處理」的錯覺，實際效用等同 `total`。

**實作鐵則：** 過濾必須在**後端 RPC** 完成。

| `detailLevel` | RPC payload 限制 |
| --- | --- |
| `total` | **不得包含任何交易列** |
| `amounts` | **不得包含 `title` / `note` / 確切 `date`**。日期於 SQL 層以 `to_char(date, 'YYYY-MM')` 截斷後才回傳 |
| `full` | 完整回傳（僅限該 scope 範圍內） |

> 若只在前端隱藏，對方按 F12 打開 DevTools 就全看到了。「前端隱藏當安全機制」是常見且嚴重的錯誤。

### 3.12 資料安全與防遺失（核心，非附屬功能）

> **問題不是「使用者不小心刪掉資料」，是「瀏覽器會自己刪掉資料」。**

#### 3.12.1 純 Web 的真實風險

| 風險 | 說明 |
| --- | --- |
| **⚠️ Safari ITP 七日清除** | WebKit 會在使用者七天未與網站互動後，清除該來源的 script-writable storage（含 IndexedDB、LocalStorage）。**使用者什麼都沒做，出國一趟回來帳就沒了。** 加到主畫面的 PWA 可豁免，但不能假設每個人都會加 |
| 瀏覽器儲存空間壓力 | 裝置空間不足時，瀏覽器會驅逐「非持久化」來源的資料 |
| 使用者清除瀏覽資料 | 一鍵清光，無警告、無救援 |
| 換裝置 / 換瀏覽器 | 本地資料完全帶不走 |
| 無痕模式 | 關閉分頁即消失 |

> **結論：純 Web + 僅本地儲存在 iOS 上不可行**，不只是「風險較高」。這使 v0.3 的雲端決策成為**必要條件**，而非加分項。

#### 3.12.2 六層防護

| 層 | 機制 | 防護對象 |
| --- | --- | --- |
| **L0** | **匿名帳號 + 自動雲端備份** | 瀏覽器清除、換裝置、ITP |
| **L1** | `navigator.storage.persist()` | 儲存空間驅逐 |
| **L2** | Undo Toast（刪除後 5 秒可撤銷） | 手滑 |
| **L3** | 垃圾桶（軟刪除保留 30 天） | 誤刪後才發現 |
| **L4** | 匯出（JSON / CSV）+ 每月提醒 | 一切災難的最後手段 |
| **L5** | 危險操作二次確認 | 批次刪除、刪除帳號 |

#### L0：匿名帳號（最關鍵的一層）

> 傳統做法要求「先註冊才能同步」。這在記帳 App 是致命的——使用者只想記一筆錢，不想填 email。

**匿名帳號 ≠ 不登入。** 是系統在背景替使用者開了一個沒有名字的帳號。

**做法：** 首次開啟 App 時，背景以 **Supabase Anonymous Auth** 建立帳號（`uid = a3f9...`），憑證存於瀏覽器。使用者**不需註冊、不需 email、不需密碼**，但從第一筆記帳起資料就有雲端副本。

**三種模式的比較**

| | 傳統「先註冊才同步」 | 「純本地不登入」 | **匿名帳號** |
| --- | --- | --- | --- |
| 首次使用門檻 | 高（要填 email） | 無 | **無** |
| 資料會不會不見 | 不會 | **會**（Safari ITP 七日清除） | **不會** |
| 換手機 | 可以 | 不行 | 綁定後可以 |

> **因此「未登入的純本地模式」不予保留。** 匿名帳號已提供零註冊門檻，且資料不會遺失。同時維護兩套路徑只會增加「本地資料上傳綁定」的邊界情況。

| 階段 | 狀態 |
| --- | --- |
| 首次開啟 | 自動建立匿名帳號，`ownerId = auth.uid()`，開始同步 |
| 日常使用 | 與已註冊使用者無差異 |
| 想換手機時 | 設定頁提示 `綁定帳號才能在其他裝置使用` → 綁定 Google / Apple |
| 綁定後 | 匿名帳號**原地升級**（同一個 `uid`），資料零遷移 |

**風險與緩解**

- 匿名帳號的憑證存在本地。若本地被清除且**未曾綁定**，雲端那份資料就再也沒人能取回——成為**孤兒資料**
- 緩解：使用滿 7 天或累積 30 筆後，Dashboard 顯示一次性提示 `綁定帳號，換手機也不怕`
- 緩解：孤兒資料（**180 天無任何存取**）自動清除。基於儲存成本與隱私責任，須於隱私政策揭露
- 提醒：使用者主動「登出」匿名帳號等同永久丟失資料。**登出前強制匯出 + 二次確認**

**⚠️ 已知限制：不支援共用裝置**

同一瀏覽器只能對應一個匿名帳號。共用電腦的兩個人會看到同一本帳，且沒有「切換使用者」機制（登出匿名帳號 = 丟失資料）。

| 現況 | MVP 決策 |
| --- | --- |
| 使用者 A、B 共用一台電腦 | **不支援。** 於「關於」頁揭露此限制 |
| 繞道 | 使用不同瀏覽器 / 不同瀏覽器設定檔 / 無痕（無痕會遺失資料，不建議） |
| 未來解法 | 綁定帳號後支援登出／切換（Phase 4 之後，已綁定者登出不丟資料） |

> 這是匿名帳號的固有代價。SayPay 是個人記帳工具，主要使用場景為個人手機，此限制可接受。

#### 登出（Phase 4 起）

**登出是必要功能，非選項**——無登出的 App 在商店審核與企業採購都會被質疑。行為依帳號狀態分兩種：

| 帳號狀態 | 登出行為 |
| --- | --- |
| 已綁定 Google / Apple | 正常登出。清除本地後資料仍在雲端，可重新登入取回 |
| 匿名（未綁定） | **強制先匯出 + 二次確認**。登出等於永久丟失（同 §3.12 登出前規範） |

**⚠️ 登出必須完整清除本地資料，否則構成資安事故。** 下一位使用者若能透過 DevTools 讀到殘留，即為跨使用者資料外洩。清除範圍**不只 IndexedDB**：

- IndexedDB（交易、結清、成員…全部 object store）
- Cache Storage 與 Service Worker 快取
- `localStorage` / `sessionStorage`（偏好設定、UI 狀態）
- 記憶體中的 Pinia store（reset）

> 已綁定者登出後可換人登入，因此**登出同時解決了共用裝置限制**（上表「未來解法」）。

#### L1：請求持久化儲存

```js
if (navigator.storage?.persist) {
  const granted = await navigator.storage.persist()
  // granted === false 時，於設定頁顯示「建議將 SayPay 加到主畫面以確保資料安全」
}
```

- Chrome 依使用者參與度自動授予
- Safari 對「已加到主畫面」的 PWA 較寬容
- **首次開啟時引導「加到主畫面」**，這同時提升 persist 機率並豁免 ITP 七日清除

#### L2：Undo Toast

刪除任何交易 / 結清後，底部顯示 `已刪除 · 復原`，5 秒內可撤銷。此期間**不送出同步請求**（避免無謂往返）。

#### L3：垃圾桶

- 所有刪除皆為軟刪除（`deletedAt`）
- 設定頁「垃圾桶」列出 30 天內刪除的項目，可單筆還原
- 30 天後由背景任務硬刪除
- 軟刪除的交易**不計入任何統計與債務矩陣**

#### L4：匯出

| 格式 | 用途 |
| --- | --- |
| **JSON** | 完整備份，可還原（含 `schemaVersion`） |
| **CSV** | 給人看 / 進 Excel。**寬表格式**，見下 |

**CSV 寬表格式**

一筆交易 = 一列。每位成員一欄，值為該人的 `shareAmount`；空白代表未參與。

```csv
date,title,amount,type,category,note,is_split,paid_by,我,Amy,Ben
2026-07-10,火鍋,600,expense,餐飲,,TRUE,我,200,200,200
2026-07-11,咖啡,120,expense,餐飲,,FALSE,我,120,,
2026-07-12,計程車,250,expense,交通,機場,TRUE,Amy,125,125,
```

| 規則 | 說明 |
| --- | --- |
| 成員欄位 | **只輸出這批資料實際出現過的成員**，不固定 20 欄（避免大量空欄） |
| 欄名 | 直接用成員名。同名成員以 `名字 (id前4碼)` 區分 |
| `amount` | 交易總額（現金流出） |
| `paid_by` | 誰墊的錢 |
| 驗算 | `Σ 成員欄 === amount`（`is_split = TRUE` 時） |
| 編碼 | UTF-8 **with BOM**（否則 Excel 開啟中文會亂碼） |
| 結清記錄 | 另存 `settlements.csv`（`date,from,to,amount,note`） |

- 設定頁可手動匯出
- 每月 1 號 in-app 提示一次 `要備份上個月的帳嗎？`
- **匯出功能必須在 Phase 0 完成**。它是唯一的最後手段

#### L5：危險操作

| 操作 | 確認方式 |
| --- | --- |
| 刪除單筆 | Undo Toast（可撤銷，不需事前確認） |
| 批次刪除 / 清空類別 | 二次確認 Dialog |
| 刪除帳號 | 二次確認 + 輸入帳號名 + 強制先匯出 |
| 還原備份（覆蓋現有資料） | 二次確認 + 自動先備份當前資料 |

## 4. 資料模型

### 4.1 金額表示

**所有金額以整數「分」（cent）儲存**，避免浮點誤差。顯示與結算時四捨五入到「元」。

```ts
type Cents = number  // 整數，1 元 = 100
```

### 4.2 Member

```ts
type Member = {
  id: string
  name: string         // 唯一，禁止同名
  avatarColor: string
  isSelf: boolean      // 恰有一位為 true
  deletedAt?: string
}
```

**同名禁止規則**

| 項目 | 規範 |
| --- | --- |
| 唯一性 | `name` 在未軟刪除的成員中必須唯一 |
| 正規化 | 比對前 `trim()` + 去除連續空白 + Unicode NFC。`"Amy "` 與 `"Amy"` 視為同名 |
| 大小寫 | **區分**（`amy` 與 `Amy` 視為不同）。中文為主的情境下不宜過度合併 |
| 衝突處理 | 建立時即時提示 `已有成員叫 Amy`，阻擋儲存 |
| 自然語言解析 | §3.2.2 解析出既有成員名時直接沿用，不建立重複成員 |
| 軟刪除的成員 | 名字釋出，可被新成員使用 |

> 理由：CSV 寬表以成員名作為欄名（§3.12 L4），同名會直接衝突。且分帳 UI 中兩個「Amy」在視覺上無法區分。

> 成員是**純標籤**，沒有 `userId`。MVP 中分帳對象不登入。
> `paidBy` / `members` 一律存 `Member.id`，**不使用 `'me'` 字面值**；「我」透過 `isSelf` 識別。

### 4.3 Transaction

```ts
type Transaction = {
  id: string
  ownerId: string         // Supabase auth.uid()
  title: string
  amount: Cents
  type: 'income' | 'expense'
  category: string        // categoryId（葉節點）
  date: string            // ISO datetime，本地時區
  note?: string

  // 分帳（type === 'expense' 時才有意義）
  isSplit: boolean
  paidBy: string          // memberId，單一付款人
  members: string[]       // memberId[]，1..20，可不含 paidBy
  splitType: 'equal' | 'custom' | 'percentage'
  splits: SplitItem[]

  groupId?: string        // 單值。一筆交易最多屬於一個群組。僅供檢視分組，不影響債務歸屬

  createdAt: string
  updatedAt: string
  deletedAt?: string      // 軟刪除，供同步 tombstone
}
```

### 4.4 SplitItem

```ts
type SplitItem = {
  member: string        // memberId
  shareAmount: Cents    // 此人應負擔
}
```

> **移除 `paidAmount` 與 `settled`。**
> `paidAmount` 可由 `paidBy` 推導（付款人 = `amount`，其餘 = 0），保留會造成兩處真實來源。
> `settled` 由 Settlement ledger 取代。
>
> **不變式：** `Σ splits[].shareAmount === amount`，且 `1 ≤ splits.length ≤ 20`

### 4.5 Settlement

```ts
type Settlement = {
  id: string
  ownerId: string
  from: string          // memberId，付錢的人
  to: string            // memberId，收錢的人
  amount: Cents         // > 0
  at: string
  note?: string
  deletedAt?: string
}
```

> 不含 `groupId`。這是「債務掛在人身上」的直接體現。

### 4.6 其他

```ts
type Group    = { id: string; name: string; memberIds: string[]; createdAt: string }

type Category = {
  id: string
  name: string
  icon: string
  parentId?: string      // 子分類：餐飲 → 外食 / 食材 / 零食
  sortOrder: number
  deletedAt?: string
}

type Budget   = { month: string; total: Cents; byCategory: Record<string, Cents> }
```

> `Group` 沒有 `budget` 欄位。
>
> **子分類規則（借鑑天天記帳）**
> - 僅支援**兩層**（`parentId` 不可再有 `parentId`）
> - 交易一律掛在**葉節點**（有子分類時不可選父分類）
> - **預算只設在父分類層級**（子分類支出彙總到父分類計算）
> - 分析頁圓餅圖可切換 `父分類 / 子分類` 顯示層級，並記憶上次選擇

## 5. 核心計算邏輯

### 5.1 分帳模式

| 模式 | 規則 | 校驗 |
| --- | --- | --- |
| `equal` | `amount / members.length` | 除不盡時餘數歸付款人（§5.2） |
| `custom` | 逐人指定金額 | `Σ shareAmount === amount` |
| `percentage` | 逐人指定 % | `Σ % === 100`，換算後餘數同 `equal` 規則 |

### 5.2 餘數規則

```txt
base      = floor(amount / n)
remainder = amount - base * n

每人 shareAmount = base
若 paidBy ∈ members：paidBy 額外承擔 remainder
否則：members[0] 承擔 remainder
```

**業界對照**

| 做法 | 代表 | 評價 |
| --- | --- | --- |
| 餘數歸付款人 | 多數本地記帳 App | ✅ 採用。付款人本已墊款，多算 1~19 分無感，且必定收斂 |
| 餘數分給名單前幾人 | Splitwise | 避免同人長期吃虧，但需 UI 註明，複雜度不划算 |
| 各自進位，總和 ≠ 原金額 | — | ❌ 累積誤差，禁用 |

**不做成設定項。** 20 人平分時餘數最多 19 分（不到 $0.2）。需要精確控制者請用 `custom`。

### 5.3 欠款計算（pairwise，非全域）

> **⚠️ 這是 v0.1 的關鍵錯誤修正。**
> v0.1 用全域 `netBalance(member) = Σ(paidAmount - shareAmount)`。
> 在「Amy 付款、Ben 參與、我也參與」的情境下會算出 `Amy +600`，但那 600 是 **Ben 欠 Amy**，與我無關。Dashboard 會錯誤顯示「我欠 Amy $1,200」。

**正確做法：有向債務矩陣。**

```txt
// 步驟一：由交易累積債務
for each transaction t where t.isSplit && t.type === 'expense' && !t.deletedAt:
    for each s in t.splits where s.member !== t.paidBy:
        debt[s.member][t.paidBy] += s.shareAmount

// 步驟二：由結清沖銷
for each settlement st where !st.deletedAt:
    debt[st.from][st.to] -= st.amount

// 步驟三：pairwise 淨額
net(A, B) = debt[A][B] - debt[B][A]
    > 0  → A 欠 B
    < 0  → B 欠 A
```

**Dashboard 與 1g 只呈現與「我」有關的列：**

```txt
應收 = Σ net(other, me)   where net > 0
應付 = Σ |net(other, me)| where net < 0
淨額 = 應收 − 應付
```

> 不涉及「我」的債務（Amy ↔ Ben）**在 MVP 不顯示**，但矩陣仍完整計算，供未來群組共享使用。

### 5.4 統計指標

見 §3.4。實作時「我付出去的 amount」由 `t.paidBy === selfId ? t.amount : 0` 推導。

### 5.5 債務簡化（明確不做）

Splitwise 有 “Simplify debts”（A欠B、B欠C → A欠C）。

**MVP 不實作。** 理由：
1. 使用者難以理解為何突然欠了一個沒一起吃飯的人
2. 所有債務都以「我」為端點，簡化無收益
3. 若未來開放對方登入，需列為**預設關閉**的選項

### 5.6 明確邊界

| 議題 | MVP 決策 |
| --- | --- |
| 收入分帳 | **不支援。** `type === 'income'` 時分帳 Toggle 隱藏 |
| 多付款人（各付各的） | **不支援。** `paidBy` 為單一 memberId，此情境請拆成多筆 |
| 純代墊（付款人不參與） | **支援。** `paidBy ∉ members`，其實際花費 = 0 |
| 分帳人數上限 | **20 人**（含自己） |
| 多幣別 | 不支援 |
| 群組預算 | 不支援 |
| 帳戶 / 付款方式 | **不支援**。一律只記金額 |
| 標籤（tag） | **不支援**。群組已扮演可疊加維度 |
| 一筆交易屬於多群組 | **不支援**。`groupId` 為單值 |
| 同裝置多使用者 | **不支援**。一個瀏覽器對應一個帳號 |

## 6. 資料與工程規範

### 6.1 儲存架構：Local-first + 雲端同步

> **決策：不用 LocalStorage。用 IndexedDB（本地）+ Supabase（雲端）。**

```txt
UI  ←→  IndexedDB (Dexie)  ←→  背景 sync  ←→  Supabase Postgres
                                                    ↓
                                        公開唯讀 RPC → /s/:token 分享頁
```

**為何不用 LocalStorage**（與後端決策無關，單純是技術缺陷）：

| 問題 | 說明 |
| --- | --- |
| 同步 API | 每次寫入 block 主執行緒序列化整包 JSON，數千筆時明顯卡頓 |
| 5MB 上限 | 交易量大時會撞牆，且 `QuotaExceededError` 難以優雅處理 |
| 無索引 | 搜尋、日期區間查詢只能全表掃描 |
| 無交易語意 | 寫到一半當機會留下壞資料 |

IndexedDB 非同步、無實質容量上限、有索引。配 Dexie.js 使用複雜度不高於 LocalStorage。

**為何仍需要本地層**（不直接打 Supabase）：

- 記帳是**高頻低延遲**操作，等網路往返會毀掉輸入體驗
- 離線可用是記帳 App 的基本要求（在餐廳地下室、國外漫遊）
- 同步邏輯簡單：因為 §6.2「餘額永不落地」，只需同步 `Transaction` 與 `Settlement` 兩張事實表，**幾乎不會有 merge conflict**

**同步策略**

| 項目 | 規範 |
| --- | --- |
| 寫入 | 先寫 IndexedDB → UI 立即更新 → 加入 outbox 佇列 |
| 推送 | 有網路時背景 flush outbox |
| 拉取 | 啟動時 + 每次回到前景時，依 `updatedAt` 增量拉取 |
| 衝突 | Last-write-wins（以 `updatedAt` 比較）。單人帳本衝突罕見 |
| 刪除 | **軟刪除 tombstone**（`deletedAt`），不可直接 DELETE，否則同步時會「復活」 |
| 帳號 | **首次開啟即建立匿名帳號並開始同步**（§3.12 L0）。不存在「未登入的純本地模式」 |
| 持久化 | 啟動時呼叫 `navigator.storage.persist()`（§3.12 L1） |
| 軟刪除 | 30 天後由 Supabase 排程任務硬刪除（§3.12 L3） |

**Supabase RLS**

- `transactions` / `settlements` / `groups` / `budgets`：`owner_id = auth.uid()`
- `share_links`：擁有者可 CRUD
- 分享頁**不直接查表**，走 `SECURITY DEFINER` 的 RPC：傳入 `token`，回傳限縮後的 payload。避免 RLS 寫錯導致整表外洩

### 6.2 餘額永不落地

**Transaction 與 Settlement 皆為事實記錄，所有餘額皆為衍生值（derived），永不儲存。**

這避免了「餘額與交易不一致」這類最難除錯的問題，也讓同步變得簡單。

### 6.3 編輯與刪除的連動

| 動作 | 規則 |
| --- | --- |
| 編輯已產生欠款的交易 | 允許。儲存後**全量重算債務矩陣** |
| 編輯後與既有 Settlement 矛盾 | 允許，可能出現反向欠款。儲存前警示：`此變更將使 Amy 的餘額由 $0 變為 −$200` |
| 刪除交易 / Settlement | 軟刪除 + 全量重算 |
| 重算效能 | 見 §6.3.1 |

#### 6.3.1 債務矩陣的效能策略

**先做估算，這個問題可能不存在。**

5,000 筆交易 × 平均 3 位參與者 ≈ **15,000 條 debt edge**。JS 執行 15,000 次整數加法約 **2~5ms**。矩陣重算本身完全不是瓶頸。

> **真正的瓶頸是從 IndexedDB 讀出 5,000 筆交易並反序列化（~100ms）。**
> 而那件事畫列表、算統計時本來就要做。

**MVP 策略**

- 交易陣列載入後**常駐 Pinia store**
- 債務矩陣從**記憶體**全量重算，不重讀 DB
- 僅在同步拉到新資料時才重讀 IndexedDB

**若日後真的成為瓶頸，業界的優化階梯（由簡到繁，不要跳級）**

| 層級 | 做法 | 適用規模 | 代價 |
| --- | --- | --- | --- |
| **1. 全量重算** | 每次寫入重跑整個矩陣 | < 50k 筆 | 無。**SayPay 停在這裡** |
| 2. Dirty-pair 增量 | 只重算受該筆交易影響的 pair | < 500k 筆 | 需正確處理編輯／刪除的 delta |
| 3. Snapshot + tail replay | 定期存餘額快照，只重放快照後的事件 | 事件溯源標準做法 | **違反 §6.2「餘額永不落地」**，引入快照／事件不一致的風險 |
| 4. Materialized view | 由 Postgres 計算，客戶端只讀結果 | 需伺服器端一致性時 | 失去離線能力 |

> **不要預先優化。** Phase 3 做一次 benchmark（目標：5,000 筆 × 20 人 < 50ms），通過就不再碰。
> 特別注意第 3 層：快照本質上就是把餘額落地，會抵銷 §6.2 費力建立的不變式。除非規模真的到了，否則不值得。

#### 6.3.2 若 benchmark 未達標：先定位瓶頸

> **多數人會往錯的方向優化。** 上表的 1~4 層全部是在優化 **CPU（矩陣計算）**。但真正的瓶頸幾乎總是 **I/O（IndexedDB 讀取與反序列化）**。
> 若瓶頸在反序列化，做增量計算或快照**一點用都沒有**——矩陣算得再快，資料還沒讀出來。

**定位方法**

```js
performance.mark('read-start')
const txs = await db.transactions.toArray()   // ← 反序列化在這裡
performance.mark('read-end')

performance.mark('calc-start')
const matrix = buildDebtMatrix(txs)           // ← 矩陣計算在這裡
performance.mark('calc-end')
```

**若瓶頸在反序列化（預期情況），正確的優化方向（按 CP 值排序）**

| # | 做法 | 說明 | 是否動搖 §6.2 |
| --- | --- | --- | --- |
| **1** | **Web Worker 反序列化** | 將 IndexedDB 讀取與 `JSON.parse` 移出主執行緒。UI 不再凍結，體感問題立刻解決一半 | 否 |
| **2** | **精簡投影表** | 債務矩陣只需 `{id, paidBy, splits, deletedAt}`，不需 `title` / `note` / `groupId`。另存一張僅含這些欄位的 `debt_projection` 表，資料量小一個數量級 | 否（仍是 derived） |
| | | **MVP 不預建**（見下） | |
| **3** | 按月分塊載入 | 帳本列表只讀當月；矩陣讀投影表全量 | 否 |
| 4 | 壓縮儲存格式 | 以陣列取代物件（省欄名字串），或存 MessagePack | 否 |

> 前三項皆不觸碰「餘額永不落地」的不變式。**快照（上表第 3 層）會**——這是它排在最後的原因，不是它最複雜，而是它最危險。

#### 6.3.3 為何不預先建投影表

`debt_projection` 是 **derived**——它只是 `Transaction` 的欄位子集投影，沒有獨立真實來源，遵守 §6.2「餘額永不落地」的同一條原則。

**這意味著日後要加它，migration 成本趨近於零：** 建表 → 掃一次 `transactions` → 寫入。不需資料轉換、不需版本相容、寫壞了刪掉重建即可。

> 「之後建需要 migration」的顧慮在 derived 表上不成立。既然延後沒有成本，就沒有理由現在建。這是預先優化。

**相關決策：`splits` 維持內嵌於 `Transaction`，不正規化為獨立表。** 內嵌讓寫入是單一原子操作，同步 payload 是單一 row。分離的好處只在效能，而效能問題尚未出現。

### 6.4 ID 與時間

- 主鍵 ID：`crypto.randomUUID()`（客戶端生成，避免同步時等待伺服器）
- 分享 token：`nanoid(16)`
- 時間：ISO 8601 字串，**日期歸屬一律以本地時區判定**（凌晨 1 點的消費算當日）
- 排序：`date` 相同時以 `createdAt` 次序排

### 6.5 校驗

所有寫入前經 Zod schema 校驗，含：

- `Σ shareAmount === amount`
- `1 ≤ splits.length ≤ 20`
- `Settlement.amount > 0`
- `Member` 中恰有一位 `isSelf === true`

**Supabase 端需獨立再驗一次**（DB constraint / trigger）。客戶端校驗不可信。

### 6.6 匯出與備份

見 §3.12 L4。JSON（完整備份、可還原）+ CSV（人可讀）雙格式。

> 即使有雲端，仍需保留匯出功能：使用者有權帶走自己的資料，這也是多數地區隱私法規的要求。**且雲端也可能出事。**

## 8. 路線圖：Web-first → App

> **決策：先做 PWA 網頁版驗證需求，之後以 Capacitor 包成 App。**

### 8.1 理由

| 面向 | 說明 |
| --- | --- |
| **分享連結天生是網頁** | 沒有人會為了看一筆 $200 的火鍋錢下載 App。這功能強制你先有可直接開啟的網址 |
| **Capacitor 重用率 ~95%** | 它把 web build 塞進 WebView 再補 native plugin。先做 web 不浪費 |
| **App Store 審核** | 對「純 WebView 包裝」審查嚴格，通常要求有 native 功能（推播、相機、Widget）才給過。現階段沒有，直接送審大概率被打回 |
| **PWA 已足夠驗證** | 可加到主畫面、全螢幕、離線、圖示。MVP 需求全滿足 |

### 8.2 為了日後 Capacitor，現在就要遵守

1. **不用 SSR**，純 SPA 靜態 build
2. **所有 API 走絕對 URL**，不依賴同源
3. 不使用 `window.location` 做路由假設
4. 檔案下載（匯出）抽象成一層 adapter（web 用 Blob，native 用 Filesystem plugin）

### 8.3 何時真的需要 native App

| 觸發條件 | 需要的 native 能力 |
| --- | --- |
| **iOS 語音輸入要能用** | native speech plugin（**最主要的理由**） |
| 預算超支要推播提醒 | Push Notification |
| OCR 發票辨識 | Camera |
| 主畫面 Widget | Native widget |

## 10. 未來擴充

### 10.1 長期最有價值的一項

**發票載具自動記帳（Phase 12）**

天天記帳與簡單記帳皆已支援：綁定手機條碼載具後，雲端發票自動匯入為記帳，使用者只需分類。這是台灣市場的殺手鐧。

對 SayPay 尤其關鍵：**它能讓「記帳」那一半近乎自動化，使產品完全專注於「分帳」這個差異化價值。**

需串接財政部電子發票整合服務平台 API。工程量不小（載具驗證、發票明細解析、去重、與手動記帳的合併），但戰略價值最高。

### 10.2 其他

- 分帳對象也能登入（屆時啟用完整債務矩陣、考慮 §5.5 債務簡化選項）
- 即時同步（Supabase Realtime）
- OCR 紙本發票掃描
- LINE Bot 記帳
- 匯出 Excel / PDF
- 多幣別（旅遊分帳的最大缺口）
